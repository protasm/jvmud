=== Architecture

JVMud separates compilation, engine behavior, hosted instances, transport,
and persistence. A player connects through transport to a hosted mudlib instance;
that instance runs LPC content compiled for the JVM and uses engine services.
The following responsibilities define the package boundaries.

The engine is the center of the architecture. It owns JVMud truth: the world
model, canonical state machinery, and rules that should still make sense in a
non-Telnet, non-LPC, test-only JVMud world. That includes Places, Entities,
Locations, Links, Personas, Sessions, world time, mudlib boundary events, and
the `WorldRuntime` that enforces engine rules such as single containment and
valid movement.

The compiler feeds the engine by turning LPC source into executable JVM code.
Compiler packages own preprocessing, scanning, parsing, semantic analysis, IR,
bytecode generation, efun contracts, generated-code helpers, and LPC runtime
loading. Compiler helper classes support generated bytecode; they do not define
the engine ontology.

The mudlib is the authored world. It supplies LPC content, fiction, object
behavior, commands, rules, and compatibility policy. Mudlibs are deliberately
outside the JVMud Java package tree and live under `mudlibs/`, because they are
content hosted by JVMud rather than JVMud engine code.

Persistence sits beside the engine because durable state is a cross-cutting
storage concern, not an engine ontology concern. Filesystem and JDBC adapters
belong in persistence packages so the engine and instance layers can ask for
durable services without embedding file formats or database details.

The instance layer is one live hosted realization of the architecture. It boots
a mudlib, assembles compiler output with engine state, owns the active
`WorldRuntime` object for that hosted world, attaches Personas, dispatches
mudlib lifecycle hooks, and routes mounted mudlib worlds through the
`MudlibRouter`. The instance is concrete in a way the engine is not: it knows
which mudlib is booted, which LPC objects are loaded, and which players are
currently attached.

The transport layer is the human connection boundary. Telnet code owns sockets,
sessions, echo behavior, line input, output delivery, and connection lifecycle.
Transport turns a human connection into input for an instance; it does not own
world rules.

The player is at the bottom because all of this machinery exists to create an
interactive, player-present text world. A player reaches JVMud through a
transport, enters a running instance, experiences engine-owned world reality
through a Persona, and interacts with mudlib-authored behavior compiled into
JVM code.

As a rule of thumb: if a concept defines what JVMud means by a world, it belongs
near `engine`. If it exists because a particular hosted mudlib is running, it
belongs near `instance`. If it speaks a connection protocol, it belongs near
`transport`. If it stores durable state, it belongs near `persistence`. If it is
authored LPC content, it belongs in a mudlib.
