=== Architecture

JVMud has four top-level Java packages: `language`, `engine`, `communication`,
and `storage`. The names describe ownership so a reader can find the major
pieces before learning their classes. Package-level Javadocs explain each
subpackage's contract and its collaborators.

`language` owns LPC semantics and the machinery that represents and executes
LPC programs. `compiler` groups preprocessing, scanning, tokens, parsing, types,
semantic analysis, IR, bytecode generation, and the compilation pipeline.
`execution` supplies compiled-class and object invocation contracts. `runtime`
defines the context used by generated bytecode and implements operations on LPC
values. `efun` defines the callable contract and language-only built-ins;
`formatter` handles source layout.
Language code does not own worlds, connections, manifests, or storage adapters.

`engine` separates three central responsibilities:

* `application` starts JVMud, owns public endpoints and administrator authority,
  supervises separate worker JVMs, and supports installation updates. It remains
  available with zero mudlibs.
* `model` defines worlds, Places, Entities, Locations, Links, identities, time,
  and mudlib lifecycle contracts. `WorldRuntime` enforces single containment and
  valid movement. The model does not read manifests or operate sockets.
* `instance` assembles language facilities, model state, and host services into
  one running mudlib. `lpc.MudlibRuntime` loads authored behavior;
  `lpc.MudlibRuntimeContext` implements its interaction with the engine.
  `lpc.LPCInvocationStack` owns current/previous-object identity and call scopes;
  `lpc.LPCMethodInvoker` owns method selection and argument adaptation.
  `lpc.LPCObjectLifecycle` owns live receivers and behavior replacement.
  `lpc.LPCCommands` owns command context, action registration, and dispatch.
  `efun.EngineEfuns` composes language-only functions with engine-service adapters.
  Input, administration, and ticks run on the instance's execution queue.

The engine's `configuration` package interprets manifest policy for the
application and instance. Optional LPC syntax is described by the language's
`compiler.LanguageFeature`; a manifest selects it. The `diagnostics` package
runs compilation checks against configured mudlib startup content.

`communication` owns human-facing interaction. Its `transport` packages handle
sockets, Telnet, administration framing, and connection lifecycle. Its `admin`
package interprets administrative commands and maintains session state; its
`console` package supplies the terminal client. Structured client messages and
text presentation live in `protocol` and `output`. Player commands continue to
be interpreted by the mudlib.

`storage` owns durable representations and adapters, including filesystem
accounts, LPC object state, JDBC services, and administrator identities and
grants. The engine selects these adapters; the language does not instantiate
them.

The mudlib supplies authored content, fiction, object behavior, player commands,
and compatibility policy. It lives under `mudlibs/`, outside the Java package
tree. A player connects through communication code to an engine instance,
which runs compiled behavior against model state and storage services.

These packages organize responsibilities within one Maven artifact. Separate
worker JVMs give each mudlib independent runtime state and contain worker process
crashes. Workers retain the host account's OS permissions; this architecture
provides fault isolation, not an OS security sandbox.
