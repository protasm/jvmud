=== Architecture

JVMud has four top-level Java packages: `language`, `execution`,
`communication`, and `storage`.

`language` turns LPC source into executable JVM code and supplies the runtime
support that code needs. It owns preprocessing, scanning, parsing, semantic
analysis, IR, bytecode generation, efun contracts, loading, and diagnostics.

`execution` separates three responsibilities:

* `application` starts JVMud, owns public endpoints and administrator authority,
  supervises sandboxed worker JVMs, and supports installation updates. It remains
  available with zero mudlibs.
* `model` defines worlds, Places, Entities, Locations, Links, identities, time,
  and mudlib boundary contracts. `WorldRuntime` enforces rules such as single
  containment and valid movement. These concepts do not own process supervision.
* `instance` assembles language runtime facilities and model state into one
  running mudlib. It boots content, attaches Personas, invokes lifecycle hooks,
  and serializes input and ticks on the worker's execution queue.

`communication` owns human-facing interaction. Its `transport` packages handle
sockets, Telnet, administration framing, and connection lifecycle. Its `admin`
package interprets administrative commands and maintains session state; its
`console` package supplies the terminal client. Structured client messages and
text presentation live in `protocol` and `output`. Player commands continue to
be interpreted by the mudlib.

`storage` owns durable representations and adapters, including filesystem
accounts, LPC object state, JDBC services, and administrator identities and
grants. Execution uses these services without owning their storage formats.

The mudlib supplies authored content, fiction, object behavior, player commands,
and compatibility policy. It lives under `mudlibs/`, outside the Java package
tree. A player connects through communication code to an execution instance,
which runs language-compiled behavior against model state and storage services.

These packages organize responsibilities within the project. The worker process
sandbox, rather than a Java package name, enforces isolation between mudlibs and
the supervising application.
