=== Compatibility Shims

Keep imported source as upstream material. Put compatibility functions, aliases,
headers, and lifecycle translations in the profile's `jvmud/` area where possible.
`mfun_object` supplies mudlib-global helpers; `compatibility_object` and
`compatibility_overrides` support explicit compatibility overrides.

For a missing legacy operation, first identify whether the gap is syntax, a
native engine operation, or profile policy. Add generic compiler/engine behavior
only when it belongs to JVMud; map legacy vocabulary in the profile. Do not relax
explicit typing to accommodate an untyped legacy declaration.

Record the motivating source and test in `docs/COMPATIBILITY_FEATURE_PROVENANCE.md`
when changing compatibility features. The result should remain usable without
hardcoding a particular game into shared Java or launch scripts.

==== Opt-In Legacy Method Transpilation

A bridge manifest may explicitly set `transpilation.untyped_methods = true`.
The default is false. JVMud's `io.github.protasm.jvmud.compiler.transpiler` subpackage
adds explicit `mixed` return and parameter types to untyped method signatures
in memory after preprocessing and before parsing. Includes, inherited objects,
and global helper objects use the same profile setting. Existing explicit types
and method bodies remain unchanged, and inserted tokens retain the original
source locations. The compiler still rejects missing explicit method types when
transpilation is disabled. This accommodation does not imply support for every
legacy LPC dialect feature and never rewrites imported files.

==== Opt-In Dynamic Value Typing

Set `compiler.dynamic_types = true` when a mudlib's value declarations are
documentary. The default is false. The compiler retains written type names but
uses stable `mixed` storage for fields, locals, parameters, return values, and
typed function literal declarations. Array declarations impose no restriction.
Includes, inheritance, global helpers, and hosted bridge objects use the same
policy. Assignments cannot narrow storage after compilation.

Modifiers, argument structure, native function contracts, explicit conversions,
and runtime operation checks remain in effect. Duplicate methods of the same
arity remain errors. Missing declarations require the separate untyped-method
switch. Mixed defaults and empty returns use LPC zero. Existing unsupported
syntax, including legacy casts, remains unsupported.

LP245 selects this policy instead of its former 51 field and 24 local type
overrides. Its JSON file retains only the method-varargs rule for `room/room.c:init`.
Remove field/local type overrides before enabling dynamic typing; combining them
is rejected. Checked overrides remain available for mudlibs using strict typing.

Restart the instance when changing typing policy so every object is recompiled
under the same policy.

==== Checked Field-Type Overrides

Select a bridge-owned JSON file explicitly in the manifest:

[source,properties]
----
transpilation.overrides = transpilation.json
----

The override file path is relative to the manifest directory. This setting is
independent of `transpilation.untyped_methods`; neither enables the other.

[source,json]
----
{
  "field_type_overrides": [
    {
      "file": "obj/torch.c",
      "field": "amount_of_fuel",
      "expected_type": "string",
      "replacement_type": "int"
    }
  ]
}
----

`file` identifies a filesystem compilation unit relative to `mudlib_root`.
Rules apply after preprocessing, so declarations expanded from its headers are
part of that unit. They also apply when the unit is loaded as an inherited
object, global helper, or bridge object. In-memory snippets without a source
file path are not matched by file overrides.

The named field must occur exactly once with the expected type. A mismatch,
missing field, or duplicate declaration stops compilation at the `TRANSPILE`
stage. Invalid JSON, unknown keys, duplicate rules, missing source files, and
unsupported field types are errors. Fields can use `int`, `float`, `string`,
`object`, `mixed`, `mapping`, `function`, or `status`, with optional array stars.
The JSON vocabulary also supports `local_type_overrides` and
`method_varargs_overrides`; those adaptations are separate from field rules.

Grouped declarations are split when necessary to preserve neighboring fields'
types, modifiers, and initializer order. Locals, parameters, method bodies, and
string values are not field override targets. Source locations are retained for
diagnostics and original files are never rewritten. Rules are read at manifest
load; restart the instance to load changed configuration.
